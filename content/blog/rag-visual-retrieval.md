有个客户给了一批研报，让我们做问答。

第一版跑出来，问「2024 年 Q3 的毛利率」，模型引用了两张不相干的表。查了半天，问题在 OCR：双栏排版被从左到右扫成一行，左栏的结论和右栏的数字粘在一起，切块之后语义就散了。

那是我们第一次认真考虑，是不是可以不解析。

## OCR 这条路的三道坎

第一道是阅读顺序。双栏还算好的，三栏加侧边栏的版式，按坐标扫出来的顺序基本没法看。我们试过用版面分析重排，能救回大部分，但页眉页脚、图注、脚注混进来的情况还是得靠规则补。

第二道是表格。一张跨页的利润表，表头在第一页、数据在第二页，切开之后两半各自成立、合起来失效。图表更没办法，OCR 只能拿到图注和坐标轴，图里的数字一个都进不了索引。而用户问的往往就是图里的数字。

第三道是错误会传下去。OCR 错一个数字，embedding 就偏一点；版式还原错一次，chunk 边界就错一次。这些错误不会在检索阶段报出来，只会表现成「答得似是而非」，你很难分清是检索错了还是模型编了。

## 把页面当图片

2024 年底 ColPali 给了一个很直接的方案：不解析了，页面渲染成图，用视觉模型编码。

一页 A4 大约切出一千个 patch，每个 patch 过一遍 VLM，投影成 128 维向量。一页文档就变成一组向量，而不是一段文本。

查询侧还是文本，用同一个模型的文本塔编码成 token 向量，两边用 late interaction 打分：每个 query token 找最像的 patch，再求和。

单向量做不到这个。整页压成一个点之后，表格、脚注、免责声明共享同一个坐标，相似度被平均掉了。多向量保留了局部性，问「毛利率」只会跟表格附近那几个 patch 高分。

| 维度 | OCR 加文本 RAG | 视觉检索 |
|---|---|---|
| 表格结构 | 靠解析器，跨页易断 | 原样保留 |
| 图表数字 | 基本丢 | 留在图里 |
| 阅读顺序 | 要版面模型 | 不涉及 |
| 精确字符串 | 强 | 弱，得配 BM25 |
| 索引体积 | 小 | 大十几倍 |

## 打分很简单，存储才是问题

向量归一化之后，一页和一个查询的相关性就是：

```python
def maxsim(query_vecs, page_vecs):
    sim = query_vecs @ page_vecs.T          # (n_q, n_p)
    return float(sim.max(axis=1).sum())
```

GPU 上几千页打分也就几毫秒。真正贵的是存：一页约 1030 个 patch、128 维、bf16，算下来 264KB。一百万页就是 264GB。

我们用了三招压到 60KB 左右：相邻 patch 池化到 512；PCA 降到 64 维；int8 量化，查询侧再用 float 重打分。

| 方案 | 每页 | 召回@5 |
|---|---|---|
| bf16 原始 | 258MB / 千页 | 91.4 |
| 池化到 512 | 128MB / 千页 | 90.8 |
| 加 PCA 64 | 64MB / 千页 | 89.9 |
| 加 int8 | 32MB / 千页 | 89.1 |

掉两个点换八倍存储，这笔账我们觉得划算，因为文本管线的上限本来就更低。

生产上也不对全库做 MaxSim。先用池化后的单向量 ANN 召回 200 页，再做完整精排，P95 从 480ms 降到 90ms。

## 查询侧才是真功夫

页面编码是离线的，查询是实时的。文本和图像之间的语义差，得靠 query 补。

必须用同一个模型编码，混用别的 embedding 会让向量空间错位。这是最容易犯的错，我们第一次就踩了，换回同一个文本塔之后召回立刻正常。

另一个是 query augmentation：先让 LLM 写一个假答案，跟问题拼起来再编码。因为文档里的措辞往往和用户提问不一样，假答案能补上文档侧的用词。

```python
def augment(question, llm):
    draft = llm.complete("用一段话回答，不需要准确，覆盖术语即可：" + question, max_tokens=120)
    return question + "\n" + draft
```

财报类问题上，这一步把 Recall@5 从 82% 拉到 89%。代价是每次多一次小模型调用，一百多毫秒。

精确匹配还是得靠 BM25。合同编号、产品型号这类查询，向量检索天然不擅长，我们两路并行召回再融合。

## 生成时把图喂回去

检索到 top-k 之后，可以把 OCR 文本塞回 prompt，也可以直接把页面图当视觉上下文传给 VLM。

我们选后者。OCR 已经丢过一次信息，塞回去等于把损失固定下来。VLM 直接看页面，表格的行列结构、图表的趋势、盖章和手写批注都还在。

代价是 token。一页图一千到一千六百个视觉 token，五页就是七八千。我们的策略是默认三页，按 rerank 分数动态调；超过四页改走先摘要再回答。

引用也要落到坐标。patch 和页面是线性映射的，模型指向某个 patch，我们就能换算成矩形框，前端在页面上画出来。合同、财报场景里这点很关键，没有框，业务方不会信。

```python
def patch_to_bbox(idx, grid=(32, 32), page=(1240, 1754)):
    cols, rows = grid
    w, h = page[0] / cols, page[1] / rows
    r, c = divmod(idx, cols)
    return (c * w, r * h, (c + 1) * w, (r + 1) * h)
```

## 什么时候别用

纯文本语料别用，制度、FAQ、代码库，文本 RAG 更便宜也更好调。

对精确匹配要求高的别用，法条编号、SKU、股票代码，必须混 BM25。

扫描质量差的别用。我们测过，150dpi 以下的扫描件，patch 里全是噪点，视觉检索反而不如 OCR。

预算紧的也别硬上。一页编码单卡 A10 大概 40ms，百万页要跑十几个小时，存储还是文本的十倍。

## 最后

1200 页混合语料上，文本管线的 recall@5 是 71%，视觉检索 89%。拆开看，图表类问题的差距最大，纯文字类基本持平。

跨页表格仍然会挂，精确编号还是靠 BM25。

但至少「版面」这件事，我们不用再假装它不存在了。
