财务把上个月的模型账单发过来，四万八。

立项的时候我们按每任务五毛做的预算，实际跑下来一块五，三倍。处理了三万两千个任务。

那天下午拆账，发现三件事：所有任务无差别用最大模型；缓存命中率 11%；失败任务的平均成本是成功任务的 2.8 倍。

最后一条最肉疼。失败的任务会在重试里反复烧钱，一直烧到熔断才停。钱花了，什么都没有。

## 为什么 Agent 比聊天贵

聊天是一次交互一次推理。Agent 不是。

一个稍微复杂点的任务，可能触发十几二十次调用：规划一次、每个工具前后各判断一次、失败重试几次、最后汇总一次。同样的单价，乘以十几倍，量级就变了。

公开数据里推理成本已经占企业 AI 预算的大头，大概 85%。所以成本这事不是「省钱技巧」，是能不能规模化的问题。

## 缓存被一个时间戳干掉了

缓存的前提是前缀稳定。我们的 system prompt 里写着这个：

```text
当前时间：2026-10-23 00:41:07
用户：张三
```

精确到秒，每次请求前缀都不一样，命中率直接归零。

改法很朴素，把所有易变字段挪到 system prompt 后面：

```python
def build_messages(ctx):
    prefix = [SYSTEM_RULES, TOOL_SCHEMA, EXAMPLES]   # 稳定，参与缓存
    dynamic = [f"当前时间：{ctx.now}", f"用户：{ctx.user}", ctx.history]
    return prefix + dynamic
```

就这一处，命中率从 11% 到 60% 多。省下来的主要是输入 token，账单上很直观。

## 该用小模型的步骤，别给大模型

第二个杠杆是按步骤分模型。

大多数 Agent 的调用里，真正需要大模型的只有规划和复杂判断，其余大量机械步骤完全可以用小模型：

```python
ROUTE = {
    "plan": "large",
    "judge_complex": "large",
    "extract_id": "small",
    "classify": "small",
    "format": "small",
}

def pick_model(step):
    return MODELS[ROUTE.get(step.kind, "medium")]
```

我们把「提取工单号」「判断是不是退款类问题」「格式化输出」这三类路由到小模型，整体成本降了六成左右，任务成功率基本没动。因为这些步骤本来就不需要推理能力。

判断标准很好用：这一步的输出空间是不是很小。选择题、抽取题、格式化题，交给小模型；只有开放式的规划和权衡，才值得上大模型。

## 延迟

平均延迟没意义，用户记住的是最慢的那次。

Agent 的尾部延迟一般由三件事决定：工具串行等待、长上下文、重复推理。

工具等待通常占四到六成，却最容易被忽略，因为它在 trace 里只是一段空转，不计入模型耗时。无依赖的工具并行调用，总耗时就能压到最慢的那个。

首字慢靠流式，重复推理靠请求合并和结果缓存。公开的复合推理架构报告里，有团队用这套组合把 P95 降了一半以上、吞吐提了几倍、成本还降了三四成。降延迟和降成本在这里不冲突。

## 账本重构的顺序

后来我们把优化过程记了一下，顺序其实比动作重要：

| 阶段 | 做了什么 | 单任务成本 |
|---|---|---|
| 优化前 | 全量大模型 | $1.50 |
| 第一步 | 修缓存前缀 | $1.05 |
| 第二步 | 机械步骤路由小模型 | $0.72 |
| 第三步 | 失败快速终止 | $0.58 |
| 第四步 | 工具并行 | $0.55 |

成本下降主要在前两步，但第三步对稳定性的贡献最大。失败任务从成功任务的 2.8 倍降到 1.3 倍，账单方差小了，而预算是按峰值做的。

顺序也有讲究：先修缓存，零风险收益大；再动路由，要评估质量；最后才碰重试策略，因为它影响成功率。反过来做，很容易在降成本的同时把可靠性搞坏。

## 最后

现在每个任务都带预算，超了就中止，不等账单出来。

这套东西没有什么惊艳的技术，都是常识。但常识要有人执行，而且要有人愿意承认「我们的缓存命中率只有 11%」这种事。

那天的账单我留着。下次有人提「上更大的模型」，我先给他看这个数。
