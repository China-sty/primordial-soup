工程师每天产出两样东西：让 AI 干什么，和最终改了什么。

前者在对话框里，后者在 Git 里。大部分团队两样都没存，或者存了没人看。

我们想回答的问题很具体：这个 bug 到底是哪次改动引入的。为了这个，把两类数据对齐了。

## 两种数据

Prompt 是意图。想做什​么、给了什么上下文、用了哪个模型、试了几轮才满意，这些只在对话流里，提交记录里一个字都没有。

Commit 是事实。改了什么、哪几行、什么时候合的、谁审的，Git 里清清楚楚，但看不出为什么这么改。

单独看都不稀缺。合起来才能回答：这行代码是 AI 生成的吗，用的什么提示；同一个 bug 反复出现，是不是某类 prompt 的固定失败模式；故障的根因提交，是哪个 Agent 在哪轮对话里产出的。

## 数据模型

采集用的是 git-ai，它把每一行 AI 代码和产生它的 prompt、模型、Agent 关联起来，元数据走 Git Notes，不污染提交本身。

落库之后是五个实体：

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Session | 起止时间、Agent | 一次完整对话 |
| Prompt | 原文、指纹、轮次 | 意图 |
| AIAttribution | model、agent、置信度 | 某个代码块由谁生成 |
| Commit | sha、作者、时间 | 事实 |
| CodeBlock | 文件、起止行 | 行级归属 |

关系是一条链：Session 到 Prompt 到 AIAttribution 到 Commit 到 CodeBlock。

必须做到行级，因为「哪次改的」最后要落到「哪一行」。commit 级只能告诉你这次提交用了 AI，行级才能告诉你这一行是第几轮对话补出来的。

入库前脱敏。prompt 里经常夹着真实订单号、内网地址甚至密钥，我们的规则是原文不落库、只留结构：先检测 PII 和密钥，命中就替换，再存模板。

## git blame 不够

遇到 bug，第一反应是 blame 看谁写的。但它回答的是最后修改者，不是引入者。

两个失效场景。一次全仓 prettier，blame 会被整体刷新，真正的引入提交被冲掉；bug 由两次提交共同造成，一次改默认值、一次改判断条件，blame 只看到后者。

学术上这叫 SZZ，公开研究表明复杂 bug 的召回有明显上限，超过四成归不到真正引入的提交。

2025 年前后的新思路是把「找引入提交」从排序问题改成图搜索加迭代推理。公开报告里，这类方法在 Linux 内核数据集上把 F1 从 0.54 提到 0.81。

## 时间知识图谱

我们借鉴这个思路，把仓库演化建成一张带时间方向的图。

节点是 Commit、File、Function、Developer、Issue。边有五类：MODIFIES、INTRODUCES、FIXES、BLAME、PRECEDES。

`PRECEDES` 看着平平无奇，但它是推理的约束：引入一定发生在修复之前。有了它，搜索空间从「整个仓库历史」收敛到「这条修复链附近的几十个提交」。

```cypher
MATCH (f:Commit {sha: $fix})-[:FIXES]->(i:Issue)<-[:FIXES]-(p:Commit)
WHERE p.ts < f.ts
MATCH (p)-[:MODIFIES]->(file:File)<-[:MODIFIES]-(c:Commit)
WHERE c.ts < f.ts
RETURN c.sha, c.ts, file.path
ORDER BY c.ts DESC
LIMIT 50
```

更新是增量的，新提交到达只重算受影响的子图；每周全量重建一次，修累积误差；同时留版本快照，能回到某个时间点看当时的因果链。

## 一次归因

拿一次线上故障走一遍。支付回调偶发超时，修复提交改了 `retryPolicy.ts` 的三行。

第一步，从修复 diff 里提取被改的行和一个可 grep 的短模式（`attempts <= MAX_RETRY`），沿图反查这些行的历史，拿到七个候选。

第二步剪枝，去掉纯格式化、纯注释、只碰了测试文件的，剩三个。

第三步，让 Agent 逐个读 diff、grep 关键模式、看调用方，判断是否真的引入了边界错误。

第四步打分：

```python
def suspect_score(cand, fix):
    return (0.40 * temporal_proximity(cand.ts, fix.ts)
            + 0.30 * file_overlap(cand.files, fix.files)
            + 0.20 * semantic_sim(cand.message, fix.message)
            + 0.10 * author_expertise(cand.author, cand.files))
```

| 候选 | 时间 | 改动 | 命中 | 分数 |
|---|---|---|---|---|
| 8c21e0d | 修复前 14 天 | retryPolicy.ts +6/-2 | 引入 `<=` 边界 | 0.91 |
| 2e4f1c8 | 前 21 天 | 新增重试单测 | 只动测试 | 0.34 |
| 5b7d9aa | 前 9 天 | 全仓格式化 | 无逻辑变化 | 0.12 |

最后输出的是一段人能复核的话：最可能是 8c21e0d，它把 `<` 改成了 `<=`，导致最后一次重试仍会触发回调；修复提交恰好改回了这个边界。排除了 5b7d9aa，它只改了缩进。

这里的关键是可复核。运维不需要相信 Agent，点开两个 hash 自己看一眼就行。

## 记忆

归因 Agent 的能力，很大程度取决于它记得什么。

我们分三层：常驻的项目规范，随任务滚动的工作记忆，按需检索的历史案例。

踩过最大的坑是冷记忆的粒度。早期直接存整段排查历史，结果模型把旧方案原样复述，哪怕那个方案当时就没解决问题。

后来改成按子任务阶段存：问题分析、复现、定位、编辑、验证，检索时只取同阶段的经验。同样的历史，误引用率明显下降。

检索也不是纯向量相似度，加了时间衰减和结构化过滤，否则三年前的方案会被当成金科玉律。

## 多 Agent

系统里没有超级 Agent，是四个各管一段，加一个编排。

归因侦探是核心，输入修复提交或故障单，输出候选和证据链。指派建议从 Developer-File 关系算模块专精度，结合修改耦合（改 A 常连带改 B）给 Top-3。知识沉淀把成功路径压成 Skill 写回冷记忆。代码摘要维护模块级摘要。

闭环有两个方向：经验回写，下次同类故障直接命中；权重修正，归因被人纠正后回写图的边权重。

## 取舍

成本。全量历史都过大模型不现实，我们分层用模型：小模型筛候选，只把 top-3 交给大模型做证据推理，省掉七成以上 token。

冷启动。新仓库没有历史，图是空的。这时先跑静态代码图谱加规则，至少能给「谁最熟这个模块」，等历史攒够再切 Agent。

隐私。prompt 里可能有用户数据，提交里可能有密钥，脱敏必须在入库前。另一条我们很坚持：只做系统级洞察，不做个人绩效排名。数据一旦用来考核，工程师就开始优化数据，整套体系的信号就废了。

评测。归因没有现成 ground truth，只能人工标注一批历史故障。指标用 F1@3 而不是准确率，因为产品形态是「给三个候选加证据」。

## 最后

这套系统现在跑通了数据管道和静态图谱，时间和归因还在迭代。

它的野心不是自动修 bug，是把研发过程中最容易被浪费的两类数据变成可查询、可推理的东西。

至于值不值，得看第一次有人靠它定位到一个陈年老 bug 的时候。
