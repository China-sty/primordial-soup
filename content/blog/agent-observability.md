有段时间我们的看板做得特别漂亮。调用链完整，每一步的耗时、token、成本都标得清清楚楚，UI 也好看。

一次复盘会上，有人指着第 7 步问：它为什么调这个工具？

会议室安静了几秒。没人答得上来。

看板上有 `tool=search_orders`、`latency=820ms`、`tokens=1200`，唯独没有「为什么要调」。

## 可观测性其实是两层

后来我们把这事拆开看，发现市面上大多数工具只做了第一层。

第一层是追踪：一次请求里发生了什么。计划树、工具调用、重试、子 Agent、成本归因、回放。这一层已经很成熟，Langfuse、Phoenix、LangSmith 这些工具做得都不错。

第二层是裁定：这一步该不该发生。是不是在绕圈，是不是偏离了目标，是不是越权。

第二层几乎没人做。公开的横向评测里，十几个主流平台在这一层集体缺席。它们会告诉你第 7 步调了个工具、花了 1200 token，不会告诉你「从第 7 步开始，它已经在做一件和目标无关的事了」。

于是只能自己写规则、训小模型、堆人工。这也是为什么装了工具，质量还是靠人扛。

## 健康的 trace 最会骗人

可观测性最反直觉的地方在这：一条看起来完全健康的 trace，可能对应一个已经跑偏的系统。

健康的标准是没报错、延迟正常、成本可控。跑偏的标准是做的不是该做的事。这两件事不相交。

一个 Agent 可以无比顺滑地、零报错地、低成本地，把一件错事做上三十步。

我们后来盯一个指标：单步通过率和轨迹通过率的差。单步 96%、轨迹 78% 的时候，那 18 个点就是级联传播的份额。这个数不会出现在任何一个单步看板上。

## 先用规则筛一遍

全量让模型评分太贵，全量人工不现实。我们现在先用四个规则信号跑全量，成本几乎为零：

```python
def screen(trace):
    return {
        "loop": repeat_ratio(trace) > 0.3,          # 同工具同参数反复
        "drift": goal_similarity(trace) < 0.6,      # 意图偏离目标
        "unverified_end": not trace.has_verification_evidence,
        "swallowed_error": any(s.tool_error and s.continued for s in trace.steps),
    }
```

命中任意一个，才进第二层，让模型看整条轨迹，回答三件事：目标是什么、实际做了什么、差在哪。

再往上才是人工，比例 5% 就够，但不能随机抽。随机抽到的九成是正常轨迹，人力全浪费。我们按「规则命中 + 模型分歧 + 新出现的工具组合」分层抽，样本效率高不少。

| 层级 | 成本 | 覆盖 | 干什么 |
|---|---|---|---|
| 规则 | 极低 | 100% | 拦明显跑飞 |
| 模型裁定 | 中 | 信号命中加抽样 | 判断意图漂移 |
| 人工 | 高 | 5% | 校准前两层 |

## trace 里缺两个字段

复盘的时候才发现，大部分工具的 trace 少了两个东西：`intent` 和 `goal_snapshot`。

没有 `intent`，你不知道模型当时打算干什么，只能从工具名反推。没有 `goal_snapshot`，你没法判断它是不是已经跑偏，因为目标本身在上下文里被冲走了。

我们现在强制记这两项，另外还有 `observation_digest`，工具返回的摘要。这三个字段加起来，才能回答「该不该发生」。

## 数据边界比功能重要

选型的时候，我们把「数据落在哪」放在功能对比前面。

trace 里是真实对话、真实业务数据、真实用户信息。金融、医疗、政企这类客户，基本只能选自托管，Langfuse 和 Phoenix 都能私有化部署。

一个折中做法是双写：完整 trace 留在自托管，SaaS 只收聚合指标（延迟、成本、错误率）。这样既有可观测性，又不把原始数据交出去。

## 最后

现在复盘会的第一句话不再是「看下调用链」，而是「先看轨迹通过率」。

这个顺序的变化挺小，但省了很多时间。以前我们花两个小时看一条 trace 的细节，最后发现是整体跑偏；现在两分钟就能判断该不该往下看。

看板还是那套看板，只是终于有人能回答「为什么」了。
