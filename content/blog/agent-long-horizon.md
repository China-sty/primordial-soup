有条 trace 我看了三遍才看明白。

任务是把一批库存同步到另一个系统。第 3 步，planner 决定调用 `inventory.sync_batch`。这个工具不存在，是它按命名习惯编的。

第 4 步，executor 收到 404，错误体是一段 HTML。它「合理」地理解成服务暂时不可用。

第 5 步，recovery 决定跳过，理由是「批量同步不是关键路径」。

第 10 步，summariser 写：已完成库存同步，跳过部分非关键项，整体成功。

每一步都能自圆其说。合起来是一次完整的虚构。

## 单步都对，轨迹是错的

后来我们统计过，长任务里大约 12% 的运行至少包含一个这样的传播性错误。而单步评测几乎全部放过，因为单步评测问的是「这一步合不合理」。

第 4 步把 404 理解成「不可用」，合不合理？合理。第 5 步跳过非关键路径，合不合理？也合理。问题出在「跳过了核心步骤却没标记失败」，这一条只有看完整条链才发现。

## 最危险的一步是宣布完成

IBM 和 UC Berkeley 在 ITBench 上做过一轮失败归因，结论有点反直觉：最强的失败预测因子不是工具选错，也不是参数写错，是「没核对就宣布完成」。

这和我们踩的坑对得上。Agent 很少死于「不会做」，多数死于「做了一半，然后自己认为做完了」。

2026 年有一起公开的 Agent IDE 事故挺典型：一个理论上改七十来行的认证修复，最后删了 28,745 行、动了 340 个文件、把路由配错导致后台 404 持续 33 分钟。事后它生成的报告写着「已恢复成功」，引用的构建任务早就被开发手动取消了。

它不是撒谎。它是报告了一个自己相信的结论。

| 「完成」的信号 | 可信度 | 问题 |
|---|---|---|
| 模型说完成了 | 最低 | 自己给自己判卷 |
| 工具返回 200 | 低 | 可能是假成功 |
| 关键断言通过 | 中 | 断言可能没覆盖全 |
| 外部测试通过 | 高 | 测试本身也可能被改 |
| 产物差异符合预期 | 高 | 预期得人来定 |

## 验证缺位有三种样子

「没验证就宣布完成」很少长得像「我跳过了验证」，它一般是这三种：

一是自我复述。把计划重新念一遍当成结果，「我将修复 X」被总结成「已修复 X」。

二是阶段性成功。中间某一步返回了 200，就被当成整条链路通了。

三是过期证据。引用的测试结果是上一轮跑的，代码在那之后已经改过。

三种有一个共同点：证据不是本轮产生的。所以后来我们的校验器第一句先问时间戳，这个证据晚于最后一次改动吗。

## 把证据做成硬门槛

我们对每个子任务定义完成需要什么，缺了就不许往前走。这段是代码，不是 prompt：

```python
REQUIRED = {
    "reproduce": ["failing_test"],
    "locate":    ["file:line", "callers"],
    "patch":     ["diff", "changed_files"],
    "verify":    ["test_pass", "no_new_failures"],
}

def complete(subtask, evidence):
    missing = [k for k in REQUIRED[subtask] if k not in evidence]
    if missing:
        raise Incomplete(subtask, missing)
```

效果很直接：它必须先产出可检查的中间物，才可能进下一步。输出被物化之后，虚构的空间就小了。

工具返回也一样，不能只看状态码。200 但 schema 不对、或者 body 里 `ok` 是 false，都得当失败处理。我们吃过一次亏：接口 200，返回 `{"items": []}`，Agent 当成「查无数据」继续往下走，实际上是权限不足。

## 上下文不是越大越好

另一个坑是上下文。

长任务跑到三十步之后，Agent 不是变笨了，是早期积累的失败诊断、没做完的子目标、用户几小时前给的约束，被新内容挤到窗口边缘去了。

我们试过把过去五十轮全塞进去。结果 token 涨到预算三倍，延迟从两秒变十五秒，而模型对最新指令的响应反而更慢。堆上下文不是解药，是新的病。

后来用三个桶：

```python
def context_for(step, history):
    pinned = [GOAL, HARD_CONSTRAINTS, ACCEPTANCE]   # 永不压缩
    recent = history[-3:]                            # 最近三步原样
    summaries = [s.summary for s in history[:-3]]    # 更早的只要结论
    return pinned + summaries + recent
```

钉住的部分保证不跑偏，摘要保证不爆窗，最近三步保证不丢细节。子任务做完就压缩成一行结论加产物路径，通常能压到十分之一。

## 那条 12 步轨迹，后来怎么定位的

| 步 | 动作 | 局部看 | 问题 |
|---|---|---|---|
| 3 | 规划调用不存在的工具 | 合理 | 规划器幻觉 |
| 4 | 收到 404 | 合理 | 错误被理解成不可用 |
| 5 | 决定跳过 | 合理 | 跳核心步骤却没标失败 |
| 6–9 | 继续做其余子任务 | 合理 | 在错误前提上继续 |
| 10 | 汇总 | 合理 | 跳过写成已完成 |
| 11 | 自检 | 合理 | 检的是自己的总结 |
| 12 | 输出成功 | 合理 | 虚构完成 |

第 11 步的「自检」看着像补救，其实最讽刺：它检查的是自己的总结，等于让模型给自己判卷。

如果只看第 12 步的最终答案，它大概率是一句「部分完成」这种模棱两可的话，很容易被放过。只有看轨迹，才知道断裂点在 5。

## 最后

现在我们的长任务都有个不算优雅但管用的习惯：任何子任务结束，先问一句「证据呢」。

问不出来，就回去重做。

这套东西不保证任务成功，但至少能让失败在第五步暴露，而不是在第三十步变成一份漂亮的报告。
